================================================================================
0. VERDICT
================================================================================

Adopt the specification. Every factual claim it makes about this codebase is
true, and each one was checked against the baseline rather than accepted.

The document is also, in one respect, too kind to the code. It describes the
Canvas startup defect as a race that leaves attach() "not guaranteed" to run.
It is not a race. On a cold page attach() is never called, on any machine, at
any network speed. The specification's own Phase 0 is therefore not a
reliability improvement to a flaky feature; it is the repair of a feature that
does not currently work at all.

Three corrections are required before Phase 0 is implemented. The first is
disqualifying as the specification is written:

    The fix proposed in section 12 does not work, because load() does not
    return what section 3.2 assumes it returns.

    Section 12 guards on `if (!ok || !window.minipaintCanvas) { return false; }`.
    `ok` is the resolved value of window.minipaintAssets.load(), which is
    Promise.all(...) - an ARRAY (javascript/main.js:120-123). A failed load
    resolves to `[false]`, and `[false]` is truthy. The guard passes. Section
    3.2 requires load() to be Promise<boolean>; nothing in section 12 makes it
    one, and an implementer following section 12 literally ships a guard that
    is decorative. Traced at section 2.1 below.

    This matters more than its size suggests: the whole point of Phase 0 is to
    replace an implicit timing assumption with a checked contract, and the
    proposed check is the one part that would not have checked anything.

The other two are in sections 2.2 and 2.3: attach() cannot report success to
the readiness primitive section 2.1 asks for, and the test suite that would
police all of this does not run in any automated place.

Sections 5 (UI) and 6 (performance to keep) need no change. The performance
work the specification protects is real, is present, and is worth protecting.

1. CLAIMS CHECKED AGAINST THE BASELINE
================================================================================

Each claim below was verified in the code at 009bad0b. None was taken on trust.

1.1 "loader_js() does not return the Promise" - section 1.1. CONFIRMED.

    minipaint_neo/assets.py:157 emits, verbatim:

        () => { const w = window.minipaintAssets;
                if (w && w.load) { w.load([...]); } }

    There is no `return`. The wrapper evaluates to undefined.

1.2 "surface.py awaits it as if it were awaitable" - section 1.1. CONFIRMED.

    minipaint_neo/canvas/surface.py:229-236:

        bundles = assets.loader_js(["canvas", "wangp"])
        Context.root_block.load(None, js=(
            "async () => { "
            f"await ({bundles})(); "
            f"if (window.minipaintCanvas) {{ {attach_js}(...); }} "
            "}"))

    Both halves of the defect are on adjacent lines of one file.

1.3 "Canvas startup is coupled to WanGP" - section 1.2. CONFIRMED.
    surface.py:229 requests ["canvas", "wangp"] in a single load() call, so
    section 3.2's "true only when every required URL succeeded" would make a
    WanGP 404 a Canvas failure the moment the Promise bug is fixed alone. The
    specification is right that the minimal patch is not merely insufficient
    but actively harmful: fixing the return without splitting the dependency
    converts a silent failure into a reproducible one.

1.4 "A failed script element is left behind and later treated as success"
    - section 3.3. CONFIRMED, and worse than described.

    javascript/main.js:46-47:

        const existing = document.querySelector('script[data-minipaint-bundle="' + key + '"]');
        if (existing) { resolve(true); return; }

    javascript/main.js:54-61, the error path, deletes the cache entry but not
    the element:

        delete loaded[key];
        resolve(false);

    So the second attempt finds the corpse of the first and resolves TRUE. A
    retry does not merely fail to retry - it converts a hard 404 into a
    reported success. Measured, section 2.4.

    The comment sitting on those lines claims the opposite: "Forgotten, so a
    later tab activation may try again." The comment describes the intended
    design; the code defeats it two lines above. Whoever fixes this should fix
    the comment, because it is the reason the bug is not obvious on reading.

1.5 "Every external entry point assumes the global happens to exist"
    - section 2.4. CONFIRMED, and one case is worse than "does not work".

    minipaint_neo/canvas/ui.py:83 sets _JS = "window.minipaintCanvas", and
    fourteen call sites guard on bare existence with a silent no-op. The
    Send-to path, ui.py:129-132, does not no-op:

        PICK_JS = (
            "(gallery, state, mode) => { if (W) W.mark(); "
            "return [W ? W.pickGalleryImage(gallery) : null, state, mode]; }")

    When the adapter is absent this returns null AS THE IMAGE and proceeds to
    call the backend. The user's picture is not delayed or refused; it is
    discarded, and the server is told the user chose nothing. Section 2.4 of
    the specification should name this case explicitly, because "must await
    the same readiness Promise" reads like a latency fix and this is data loss.

1.6 "A visible shell with no controller is the failure state" - section 4.
    CONFIRMED. attach() is called from exactly one place in the repository
    (surface.py:235). There is no self-attach on bundle execution, no
    MutationObserver retry, and no timeout fallback. When the single call site
    declines to call, nothing else ever will.

1.7 "The toolbar carries a permanent right offset" - section 5.1. CONFIRMED.
    style.css:245-250 is `left: auto; right: 52px;`, exactly the displacement
    section 5.2 rules out.

1.8 "The browser test pre-inlines the bundle it claims to load dynamically"
    - sections 8.1 and 11.3. CONFIRMED, and the harness says so itself.

    tests/browser_smoke.py:62-65:

        # ... this harness has no route to fetch them from, so it inlines the
        # one the canvas needs, in the order a page would end up with them.
        for name, folder in (("main.js", "javascript"), ("minipaint_canvas.js", "browser")):
            parts.append("<script>" + (ROOT / folder / name).read_text(...) + "</script>")

    window.minipaintCanvas therefore exists before any load event fires, the
    broken wrapper's undefined return is harmless in the harness, and attach()
    always succeeds. The suite reproduces the OLD synchronous availability
    model - the exact substitution section 11.3 tells a reviewer to reject.

1.9 Performance work the specification protects - section 6. CONFIRMED PRESENT.
    Pointer work is rAF-coalesced with a synchronous flush on pointerup and a
    drop on pointercancel (minipaint_canvas.js:224, 245, 966-967, 2097-2098);
    fit work is scheduled rather than run per notification (536-537); the
    integration bundles drive their timing from visibilitychange rather than
    rAF (minipaint_wangp.js:841, 902; minipaint_interop.js:1056); and the
    control plane documents cached reads for async routes precisely so Forge's
    event loop is not blocked (wangp/control.py:71-74, 319). Section 6's
    instruction to keep all of this is correct and costs the recovery nothing:
    none of it is on the startup path being repaired.

2. REQUIRED CORRECTIONS TO THE SPECIFICATION
================================================================================

2.1 load() returns an array, so section 12's guard cannot work

    This is the disqualifying item from section 0.

    javascript/main.js:120-123:

        function load(urls) {
            const wanted = Array.isArray(urls) ? urls : [urls];
            return Promise.all(wanted.map(one));
        }

    Promise.all resolves to an array of the individual results. Measured in a
    real browser against this baseline:

        typeof = object    value = [true]     truthy = true
        (failed load)      value = [false]    truthy = true

    Section 3.2 states the intended contract - Promise<boolean>, true only when
    every URL succeeded - and it is the right contract. But section 12, the
    part an implementer will copy, never reduces the array. Its guard

        const ok = await (CANVAS_LOADER)();
        if (!ok || !window.minipaintCanvas) { return false; }

    is load-bearing only through its second clause. `!ok` is false for every
    outcome including total failure.

    Required: fold the reduction into load() itself, so the boolean contract
    holds for every caller rather than at each call site -

        function load(urls) {
            const wanted = Array.isArray(urls) ? urls : [urls];
            return Promise.all(wanted.map(one)).then(function (results) {
                return results.every(Boolean);
            });
        }

    Both existing callers already treat the result as a truth value, so this
    narrows behaviour rather than changing an interface anyone depends on.
    Note that loadOnTab (main.js:91-118) forwards load()'s result, so it
    inherits the fix; the Clipboard tab (clipboard/ui.py:90) is its only
    caller and gains a meaningful return it currently ignores.

2.2 attach() cannot report what section 2.1's readiness primitive needs

    Section 2.1 requires a Promise whose success "means window.minipaintCanvas
    exists" and that "attach() is then invoked exactly once". Section 12's
    sketch has attach() returning true/false and calling markReady(uuid).

    Today attach() returns undefined on all four of its paths
    (minipaint_canvas.js:288-297): the already-attached early return, the
    missing-ForgeCanvas return, the missing-container return, and the success
    path. Two of those are failures and one is a success, and the caller cannot
    tell them apart.

    The missing-container path matters most and the specification does not
    mention it. attach() looks up `document.getElementById("container_" + uuid)`
    and returns silently when it is absent. That is a second, independent way
    to reach "tab rendered, Canvas not ready" - one that survives a correct
    loader - and any ready/failed state built only on bundle loading will
    report ready while this path has quietly failed.

    Required: attach() returns a boolean, and the readiness state is derived
    from that return rather than from the bundle Promise alone. Section 4's
    three states should be reachable from a container that never appeared, not
    only from a bundle that never loaded.

    Already satisfied, and worth not breaking: attach() is idempotent by
    `if (S.instance) { return; }` (line 289), so section 2.1's "repeated calls
    are idempotent" needs no work.

2.3 Phase 1 has nowhere to run, and "all tests pass" currently means very little

    Section 11.10 treats "all tests pass while the production path is absent
    from those tests" as a reviewer's warning sign. On this baseline it is the
    status quo, and by a wider margin than the document assumes:

    - There is no CI. The repository contains no .github/workflows directory.
      Nothing runs any test on any push.

    - tests/run.py's SUITES list does not include browser_smoke. Its docstring
      is explicit: "The browser smoke test is separate." The only suite that
      opens a browser is outside the only entry point that runs suites.

    - browser_smoke.py requires FORGE_ROOT to point at a full Forge Neo
      checkout (browser_smoke.py:45-51) and raises SystemExit without one, so
      it cannot run unattended even if it were listed.

    - The Promise contract of loader_js has no test at all. The one loader that
      IS tested is tab_loader_js (test_canvas_display.py:261) - the one that
      correctly returns its Promise (assets.py:140-143). The tested loader is
      the working loader; the untested one shipped broken. That asymmetry is
      the whole story of this regression in one line.

    Measured on this baseline: `python3 tests/run.py` exits 0 with 16 of 23
    suites skipped for missing optional dependencies (gradio, PIL, httpx). A
    green run here is compatible with two thirds of the suite never executing.

    Required: Phase 1 gains a CI job, and run.py's skip-on-missing-dependency
    behaviour is made to fail rather than pass when the dependencies are
    expected to be present. Otherwise Phase 1 produces tests that would have
    caught this regression and still does not catch the next one, because
    nothing runs them. The specification asks for the right tests; it does not
    ask for anywhere to run them.

================================================================================
3. WHY THE FAILURE IS DETERMINISTIC, NOT A RACE
================================================================================

Section 1.1 describes the failure as an ordering hazard: the await "completes
before the dynamically inserted Canvas script is guaranteed to have loaded".
That phrasing implies a fast cache or a warm connection might win the race.
None can.

`await undefined` resumes on the microtask queue, which drains before the
current task yields. Fetching, parsing and executing a <script> element is a
new task, and cannot run before the microtask queue is empty. The check at
surface.py:235 therefore runs strictly before any dynamically inserted script
executes - a cached bundle, a local file and a 200ms network all lose by the
same rule.

Reproduced against this baseline, driving the real javascript/main.js loader
and the real string emitted by assets.loader_js(["canvas", "wangp"]), with the
bundle served over HTTP behind a 300ms delay:

    at the instant the bootstrap's await resolved
        window.minipaintCanvas defined : False
        attach() calls                 : 0

    1.2s later, bundle arrived and executed
        window.minipaintCanvas defined : True
        attach() calls                 : 0     <- nobody retried

    a 404 bundle, then a retry
        first attempt resolved      : [false]
        failed <script> left in DOM : yes
        second attempt resolved     : [true]   <- the 404 now reports success

This is worth stating plainly in the specification because it changes how the
work is justified. Phase 0 is not hardening. Mini Paint's Canvas tab is
inoperative on this baseline, and section 15's first checkbox - "Mini Paint
opens with an attached Canvas controller" - is currently false for every user.

4. WHERE THE SPECIFICATION IS MORE PESSIMISTIC THAN THE CODE
================================================================================

4.1 Re-centring the toolbar removes one collision rather than creating one

    Section 5.2 treats the crop-handle collision as a cost to be paid for
    re-centring. The CSS comment at style.css:242-244 names two obstacles, not
    one:

        "a fitted image's top-left crop handle lives there, and the frame's
         grip sits at the top centre."

    The toolbar was displaced to the right to clear BOTH. Moving it from the
    top-left corner to the centre resolves the first outright: the top-left
    corner handle and a centred toolbar cannot overlap. Only the second
    obstacle survives re-centring, so section 5.2's list of permitted fixes has
    one target, not two.

    That target is also narrower than it reads. The grip is positioned against
    the FRAME, not the canvas (style.css:326-330: `left: 50%; top: -16px;
    transform: translateX(-50%)`). It can only reach a centred toolbar when the
    crop frame is both near the top edge of the work area and close to
    horizontally centred. The collision is conditional, transient and
    detectable from geometry the frame code already has - which is precisely
    the case section 5.2 makes for solving it at the grip.

4.2 Section 2.4 done properly is Phase 3's prerequisite, already paid for

    Section 2.3 keeps Canvas loading after mount because Send-to can fire
    before the tab is opened, and defers on-demand Canvas to Phase 3, which
    "requires teaching every external Send-to entry point to await
    ensureCanvasReady()".

    But section 2.4 already requires exactly that, in Phase 0: every entry
    point that can arrive before attach() "must await the same readiness
    Promise". Once that holds, the justification in section 2.3 for loading on
    page load has expired - the entry points no longer need the bundle to be
    there in advance, because they wait for it.

    This is not a contradiction and Phase 0 should still keep after-mount
    loading; changing both the readiness contract and the load trigger in one
    patch is the coupling section 11.8 rejects. It is worth recording that
    Phase 3 is smaller than it looks: Phase 0 pays its entire cost, and Phase 3
    becomes the one-line change of where the fetch is triggered, plus its
    proof.

================================================================================
5. IMPLEMENTATION CONSTRAINT THE SPECIFICATION DOES NOT ADDRESS
================================================================================

The entry points in section 2.4 are not free functions. They are Gradio `js=`
input transforms, and most return a value the backend then consumes - PICK_JS
returns [image, state, mode] (canvas/ui.py:129-132), CROP_JS returns
[fg, state, mode, box] (119-122), CANVAS_INPUT_JS returns a four-element list
(136-138).

Making these await a readiness Promise means making them async, which changes
what Gradio receives from a value to a Promise. Whether the mounted Gradio
version awaits a js= transform's return before invoking the backend, and
whether it preserves list destructuring across that await, decides the shape
of the entire section 2.4 change. If it does not await, the readiness wait has
to move behind the value - the transform returning a marker the backend
tolerates, or the Send-to chain gaining an explicit pre-step - which is a
larger change than section 2.4 implies.

This must be established in a browser against the pinned Gradio before section
2.4 is scheduled, not discovered during Phase 0. It is the one item in the
specification whose cost is genuinely unknown, and it is on the critical path
for section 15's "Send to Mini Paint works before the Mini Paint tab was
manually opened."

================================================================================
6. RECOMMENDED PHASE 0 ORDER
================================================================================

The specification's Phase 0 lists six items without order. Two of them carry
the others, and one of the six should move.

    1. load() returns a boolean (section 2.1 above).
       Everything else that guards on a load result is decorative until this
       lands. Do it first, not as part of the section 12 patch.

    2. loader_js() returns its Promise (assets.py:157).
       Make it the shape tab_loader_js already has three functions above it.

    3. Split canvas from wangp (surface.py:229).
       Two load() calls: one awaited and required, one fired and ignored.
       After 1 and 2, this is the difference between a Canvas that works and a
       Canvas that a WanGP 404 disables.

    4. Remove the failed element, or mark it (main.js:46-47, 54-61).
       Until this lands, every retry path in the recovery - including the one
       section 4 offers the user - can report success on a bundle that 404s.
       Correct the comment that claims this already works.

    5. attach() returns a boolean; ready/failed state derives from it
       (section 2.2 above), including the missing-container path.

    6. Toolbar re-centring and the grip (section 4.1 above).
       Genuinely independent of 1-5 and separately testable, which is what
       section 11.8 asks for. It can land in either order, but it should be
       its own commit.

Items 1-5 are one behavioural change - "startup has a checked contract" - and
should be one reviewable commit with the delayed-load browser test from
section 8.2 attached. Item 6 is a UI change and should carry the geometry
assertion from section 8.8. Nothing in Phase 0 needs to touch section 6's
performance work, and nothing in Phase 0 should.

================================================================================
7. SUMMARY
================================================================================

The specification's diagnosis is correct, its evidence is accurate, and its
instruction to keep the performance work while repairing the startup contract
is the right call - the two are not in tension, because none of the retained
optimisations sit on the path that is broken.

Three things must change before it is implemented:

    load() must return a boolean, or section 12's guard checks nothing.

    attach() must report success, or section 4's ready state cannot see a
    Canvas that failed for the other reason - a container that never appeared.

    Phase 1 must land somewhere that runs, or it repeats the exact failure it
    exists to prevent.

And one thing should be said more strongly than the document says it: this is
not a degraded Canvas. On 009bad0b the Canvas tab has no controller attached,
deterministically, for everyone.
