# Checks

```
pip install -r tests/requirements.txt                 # no torch, under two minutes
python -m playwright install chromium                 # for the browser suite in run.py
python tests/run.py                                   # image maths, both frontends, the workflow, WanGP, the queue, Clipboard, Canvas startup
FORGE_ROOT=/path/to/forge-neo python tests/browser_smoke.py   # the real extension in a real browser
```

`tests/run.py` says at the end how many of its suites actually ran. A suite
whose dependency is missing is skipped rather than failed, which is right for
a laptop and wrong for CI - set `MINIPAINT_REQUIRE_ALL_SUITES=1` to turn a
skip into a failure, as `.github/workflows/tests.yml` does.

Pin the whole Gradio ecosystem, not just Gradio. `tests/requirements.txt`
explains why in full: 4.40 declares `fastapi` and `pydantic` with no upper
bound and both have since moved past what it can work with, and neither
failure names its own cause.

## The Gradio the suite runs against

Pin Gradio to the version the target Forge ships, and check a change against
that one before shipping it:

```
pip install "gradio==4.40.0" "gradio-client==1.2.0" "huggingface_hub==0.24.6"
```

This is not housekeeping. Gradio's event graph behaves differently across major
versions, and a page that assembles cleanly on one can have a button that does
nothing on another. A change verified only against whatever Gradio happened to
be installed is a change verified against the wrong thing. `huggingface_hub` is
pinned because 4.40 imports a name that later releases removed.

To check a second version, build a venv for it rather than moving the system
install:

```
python3 -m venv --system-site-packages /tmp/venv-gradio6
/tmp/venv-gradio6/bin/pip install "gradio==6.27.0"
/tmp/venv-gradio6/bin/python tests/run.py
```

Nothing in `run.py` starts the WebUI. `tests/stubs/modules` stands in for the
handful of `modules.*` names the extension touches, `tests/stubs/modules_forge`
for Forge's canvas module (its markup, its hidden image textbox, and the
`ForgeCanvas` the host builds img2img with), and `tests/forge_like.py` builds
a page shaped like Forge Neo's `modules/ui.py` — the same component hooks, the
same constructor repair, the same two metaclass patches applied in the same
order (which is what makes a session rebuild of Forge's textbox lose its
`numpy=False`), the same canvases in img2img and Inpaint, an ImageStitch panel shaped like the
built-in script's (a hidden checkbox labelled with its title, an accordion,
the reference gallery with the script's id) in txt2img and img2img, and one
`gr.Tabs(elem_id="tabs")` around everything.

### The three browser suites, and why there are three

`browser_loading.py` tests the Canvas *startup contract* - the timing between
the Gradio load callback, the dynamic `<script>`, the asset route, the script
executing, and `attach()`. It serves the real bundles through the real route
over HTTP, with nothing inlined, and makes them late, missing, broken or
already loaded. It stands ForgeCanvas in rather than using the real one,
because none of what it asserts depends on how well the canvas draws, and that
is what lets it run anywhere - including CI, which is the point.

`browser_clipboard.py` tests the *Clipboard tab* - sending a picture out to
each destination, and the thumbnail grid. Both had failed in the page while
`test_clipboard_ui.py`'s 181 checks passed, for the same reason as above:
a send is a hidden box plus a Gradio event crossing the queue, and the
thumbnail size is a CSS custom property resolved by a real layout. Neither is
visible to a graph test. It stubs the Canvas too, so it runs in CI.

`browser_smoke.py` tests the *editor*, and needs the real ForgeCanvas for
that, so it needs a Forge Neo checkout and does not run in CI.

The browser suites are run in their own interpreter by `run.py`. Building a
Forge-shaped page is not a pure function of the process - Gradio keeps a
render context, the host keeps captured components, the stubs keep their
callback lists - so a suite that builds one after twenty-two others gets a
page that will not build, and fails for a reason unrelated to what it tests.

They used to be one file, and that file inlined `minipaint_canvas.js` into the
page's head because it had no route to fetch it from. That single convenience
is how a Canvas that never attached shipped behind 180 passing checks:
`window.minipaintCanvas` was already there, so a bootstrap that awaited nothing
and attached nothing still found an adapter. Neither file inlines a bundle it
claims to load any more, and `browser_smoke.py` mounts the real route on the
demo's own app.

`browser_smoke.py` needs Playwright with a Chromium (`CHROMIUM=/path/to/chrome`
if it is not where Playwright keeps it) and `FORGE_ROOT` pointing at a Forge
Neo checkout: the page loads Forge's own `canvas.js`, `canvas.css`, `script.js`
and `ui.js`, because the Canvas is the host's canvas. The unit suites use the
real `canvas.html` from `FORGE_ROOT` when it is set and a minimal copy with the
same element ids otherwise.

`test_frontends.py` prints one traceback on purpose — it breaks the Canvas to
prove the fallback catches it. `test_wangp_receiver_contract.py` and
`test_clipboard_ui.py` do the same to the WanGP tab and the Clipboard tab.
